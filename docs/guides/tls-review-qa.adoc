= TLS feature review: questions and answers

Review notes for https://github.com/thanos-community/thanos-operator/pull/644[PR #644].
This document records questions and answers as the review progresses.
The detailed feature description is in link:gated-features.md[the feature-gate guide].

== Why don't Receive hashring addresses include https://?

Receive hashrings contain gRPC targets in the form
`<pod>.<service>.<namespace>.svc:10901`.
The hashring selects the destination. The client configuration determines whether
the connection uses TLS, so these addresses do not take an `https://` prefix.

The operator enables TLS and server-certificate verification for Receive
forwarding and replication with:

[source,text]
----
--remote-write.client-tls-secure
--remote-write.client-tls-ca=/etc/thanos/tls/ca/ca.crt
----

Despite their `remote-write` prefix, these flags configure Receive's gRPC clients
that connect to other receivers. Thanos keeps this naming for historical reasons.
The destination secures its gRPC listener with `--grpc-server-tls-cert` and
`--grpc-server-tls-key`. Its certificate must cover the hashring hostname;
generated Receive certificates include a wildcard for pods beneath that
workload's Service DNS name.

Incoming remote write from Prometheus or a stateless Ruler uses a separate HTTP
endpoint, such as `https://<receive-service>.<namespace>.svc:19291/api/v1/receive`.
That URL does require `https://`. Receive secures that listener with
`--remote-write.server-tls-cert` and `--remote-write.server-tls-key`.

The two connections are:

* Client to Receive: HTTPS on port 19291.
* Receive to ingester: gRPC with TLS on port 10901.

The Receive case in `test/integration/featuregates/tls/tls_test.go` asserts the
client and HTTP listener flags. Its shared helper checks the gRPC listener flags
and certificate identities. Live traffic verification belongs to
`test/e2e/core-tls`.

== Did you read Thanos PR #8594?

Before this question, the implementation had been checked against the Thanos
v0.42.0 source, but the PR discussion had not been read. The merged Query changes
and relevant review comments in
https://github.com/thanos-io/thanos/pull/8594[Query: Support per endpoint TLS configuration]
have now been reviewed. The PR merged on May 4, 2026.

This is the upstream configuration support used by our Query builder:

* `default_client_config.tls_config` supplies shared TLS settings, including the
  public CA file and `enabled: true`.
* Each endpoint's `client_config.server_name` supplies its Service DNS identity
  for certificate verification. `server_name` is alongside `tls_config`, not
  inside it.
* Query reads the generated configuration through `--endpoint.sd-config-file`.
  The PR deprecates its older `--grpc-client-tls-*` flags.

A representative configuration is:

[source,yaml]
----
default_client_config:
  tls_config:
    enabled: true
    ca_file: /etc/thanos/tls/ca/ca.crt
endpoints:
  - address: 10.0.0.10:10901
    client_config:
      server_name: store.metrics.svc
----

The endpoint sets its server name and inherits TLS settings from the default
configuration. This is the structure generated by `tlsEndpointConfig` in
`internal/pkg/manifests/query/builder.go`.

The PR also confirms the DNS limitation encountered during live testing.
In the merged `cmd/thanos/endpointset.go`, static and group targets receive
per-endpoint TLS options. The separate loop over
`dnsEndpointProvider.Addresses()` builds clients with `globalTLSOpt`, so ordinary
DNS fanout does not retain each endpoint's server name. The
https://github.com/thanos-io/thanos/pull/8594#discussion_r2767092171[review discussion]
also calls out the lack of per-endpoint overrides for DNS discovery.

Our Query controller resolves ready EndpointSlices and writes static addresses
with their Service DNS identities to the endpoint ConfigMap. This uses the PR's
configuration support while preserving verified connections to each discovered
pod. No implementation change was needed as a result of this review.

== Did you read the accepted automated per-endpoint mTLS proposal?

The intended reference was
https://thanos.io/tip/proposals-accepted/202106-automated-per-endpoint-mtls.md/[Automated, per-endpoint mTLS].
It had not been read before this question. The full accepted proposal has now
been read from its
https://github.com/thanos-io/thanos/blob/main/docs/proposals-accepted/202106-automated-per-endpoint-mTLS.md[documentation source],
and its rotation design has been compared with the released Thanos v0.42.0 code.

The proposal addresses a Query that connects to local StoreAPI endpoints and
remote clusters with different TLS requirements. Its goals are per-endpoint TLS
configuration for Query's gRPC clients and automatic certificate rotation without
restarting Thanos. It explicitly excludes HTTP TLS clients and gRPC clients other
than Query from its scope.

[cols="1,2,2",options="header"]
|===
|Aspect |Accepted proposal |Current server-tls feature

|Authentication
|Per-endpoint TLS, including mTLS when both client and server authentication are configured.
|Server TLS: clients verify servers, but servers do not require client certificates.

|Endpoint configuration
|Different TLS settings and certificate files per endpoint, allowing plaintext, server TLS, and mTLS connections.
|Generated Query endpoints use the namespace trust bundle and their individual Service DNS identities. The gate enables TLS across managed components.

|Traffic covered
|Query's gRPC connections to StoreAPI endpoints.
|HTTP and gRPC connections across managed Thanos components, plus health probes and metrics scraping.

|Certificate provisioning
|Assumes cert-manager handles certificate rotation in Kubernetes.
|Creates namespace CA/issuer resources automatically or uses a supplied issuer and trust ConfigMap, then manages workload leaf Certificates.

|Applying renewed certificates
|Re-establish gRPC connections periodically and read updated certificates during TLS handshakes, without restarting Thanos.
|Uses native server certificate reloading for leaf updates. Changes a trust-only pod-template checksum and rolls workloads when the public CA bundle changes.
|===

The rotation mechanism is relevant to this review. The proposal uses
`--grpc-server-max-connection-age` to force fresh connections and TLS handshakes,
with certificate files reloaded when their modification times change.
Thanos v0.42.0 already exposes that flag with a default of 60 minutes. Its
https://github.com/thanos-io/thanos/blob/v0.42.0/pkg/tls/options.go[gRPC TLS configuration code]
uses `GetCertificate` and `GetClientCertificate` callbacks that check certificate
and key modification times and reload changed files during handshakes.

The follow-up implementation now relies on native reloads for leaf certificates.
The main HTTPS listeners also reload certificates through exporter-toolkit, and
Receive's remote-write HTTPS listener uses Thanos's server certificate callback.
Kubernetes projects Secret changes through whole-directory volume mounts.
Initial leaf issuance and subsequent leaf changes leave the pod template unchanged.

CA trust changes need separate consideration: that same Thanos client code reads
the CA bundle into `RootCAs` when constructing the TLS configuration. A fresh
handshake alone does not rebuild that root pool. The proposal also does not
establish reload behavior for the HTTP clients covered by our feature. Frontend's
downstream HTTP transport also reads its CA when constructed. The implementation
therefore keeps rollouts for public CA bundle changes across managed TLS workloads,
using `operator.thanos.io/tls-trust-checksum`. Fresh handshakes suffice for server
leaf updates, while trust-pool changes retain the restart path.

The proposal's suggested `--endpoints.config` flag and YAML layout are design
history. Our Query configuration follows the shipped `--endpoint.sd-config-file`
and `default_client_config`/`client_config` API described in PR #8594.
The subsequent implementation change is reflected in this comparison and in the feature-gate guide.

== Is this mTLS only, and is the proposal implemented?

It is not limited to mTLS. The proposal's title emphasizes mTLS, but the
implemented per-endpoint configuration also supports server TLS, which is what
our `server-tls` feature uses. The earlier comparison placed too much emphasis
on the mTLS use case.

For server TLS, Query enables TLS and verifies the server using a CA bundle and
server name. It does not need a client certificate or client key. For mTLS, the
client also supplies a certificate and key, and the server is configured to
require and verify client certificates. In the released Thanos code, server-side
`GetCertificate` reloading is installed whenever server TLS is enabled; it does
not depend on enabling client-certificate authentication.

The proposal's two main capabilities were implemented in separate changes:

* https://github.com/thanos-io/thanos/pull/4493[PR #4493: Automatic certificate rotation without restart]
  merged on August 17, 2021. Its description explicitly identifies it as the
  second part of this proposal. It adds maximum gRPC connection age and
  certificate-file reloading for fresh handshakes, covering client and server
  certificates. Server-certificate reloading also applies to ordinary server TLS.
* https://github.com/thanos-io/thanos/pull/8594[PR #8594: Query per-endpoint TLS configuration]
  merged on May 4, 2026 and is included in Thanos v0.42.0. It adds the shared and
  per-endpoint client configuration used by this integration.

The shipped configuration syntax differs from the original proposal, and the
ordinary DNS-discovery limitation described above still applies. The proposal
should therefore be read alongside the released configuration documentation.

Our feature now uses this native support for leaf-certificate renewal across
HTTP and gRPC. The follow-up checked the HTTP listeners as well:
https://github.com/thanos-io/thanos/blob/v0.42.0/pkg/server/http/http.go[Thanos's HTTP server]
uses exporter-toolkit v0.15.0, whose
https://github.com/prometheus/exporter-toolkit/blob/v0.15.0/web/tls_config.go[TLS callbacks]
reload certificates for new connections. Receive's remote-write HTTP listener
uses the same server TLS configuration as its gRPC listener.

CA changes still roll workloads because some clients construct their root pools
only at startup. The revised live test checks replacement leaf certificates on
all seven workloads' HTTP/gRPC listeners without changing pod templates or
restarting containers. It uses fresh verified connections; it does not wait for
the default 60-minute gRPC maximum connection age or claim uninterrupted CA rotation.
